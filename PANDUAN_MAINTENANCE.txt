# PANDUAN MAINTENANCE

Update: 2 Juni 2026
Project: Absensi Android + Laravel Backend

Panduan ini dipakai untuk menjaga sistem tetap rapi setelah database dirombak besar menjadi lebih normalized dan berbasis ID.

## 1. Prinsip Maintenance

Pegangan utama:

- UI Android tetap konsisten dan tidak diubah tanpa kebutuhan jelas.
- Database memakai ID sebagai relasi utama.
- Text hanya untuk label, tampilan, export, atau kompatibilitas.
- Jangan membuat master data dari typo.
- Semua perubahan database harus bisa dijelaskan, diuji, dan jika perlu di-rollback.

## 3. Backup Sebelum Perubahan Besar

Sebelum mengubah database yang sudah berisi data sungguhan:

```bash
pg_dump -U postgres -d absensi_db -F c -f backup_absensi_db.dump
```

Restore jika perlu:

```bash
pg_restore -U postgres -d absensi_db --clean --if-exists backup_absensi_db.dump
```

Kalau masih data dummy, boleh reset:

```bash
php artisan migrate:fresh --seed
php -d memory_limit=512M artisan regions:import-sql
```

Jika ingin drop semua tabel dari PgAdmin:

```sql
DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
GRANT ALL ON SCHEMA public TO postgres;
GRANT ALL ON SCHEMA public TO public;
```

Setelah itu jalankan reset Laravel dan import wilayah seperti biasa.

## 4. Aturan Menambah Tabel Baru

Sebelum membuat tabel baru, cek dulu:

- apakah tabel sejenis sudah ada;
- apakah data itu master atau transaksi;
- apakah butuh foreign key;
- apakah butuh unique constraint;
- apakah butuh index;
- apakah dipakai offline;
- apakah dipakai export/import.

Jika data referensi dipakai banyak fitur, buat master table.

Contoh master:

```text
payment_methods
attendance_statuses
student_statuses
leave_types
teacher_categories
```

Contoh transaksi:

```text
payment_transactions
absensi
nilai
teacher_leaves
```

## 5. Aturan Menambah Kolom

Untuk relasi:

```text
pakai *_id
buat foreign key
buat index jika sering difilter
```

Untuk label tampilan:

```text
boleh text, tetapi jangan dijadikan relasi utama
```

Untuk status:

```text
pakai status_id atau enum/check constraint
```

Untuk kode unik:

```text
pakai unique constraint
```

Contoh yang benar:

```text
siswa.class_id
absensi.attendance_status_id
payment_transactions.payment_method_id
teacher_leaves.approval_status_id
```

## 6. Import Excel

Aturan import Excel:

- Excel boleh memakai nama agar mudah diisi admin.
- Backend harus mapping nama ke master ID.
- Field wajib atau format penting yang salah harus tetap gagal dengan error jelas.
- Field master opsional yang tidak cocok dikosongkan dan masuk `warnings`, bukan menggagalkan seluruh baris.
- Jangan otomatis membuat master baru dari typo.
- Tampilkan baris Excel yang bermasalah.
- Untuk master siswa dan wilayah, resolver harus memakai mode strict.
- Data Siswa memakai template dengan kolom wajib `nis`, `nama_lengkap_siswa`, `jenis_kelamin`.
- NIS duplikat, tanggal invalid, dan email invalid tetap menjadi error.
- Template Data Siswa harus menjelaskan nilai resmi `status_siswa` dan `jenis_santri`.
- Jenis santri resmi untuk input baru hanya `Santri Pondok`, `Santri Madin`, dan `Keduanya`.
- Kolom `asal_sekolah` harus cocok master `school_origins` jika diisi; typo dikosongkan dengan `warnings`.
- Kolom `kelompok_belajar` pada import siswa akan mencoba memasukkan siswa otomatis ke kelompok belajar jika nama cocok dengan master.
- Header lama `kelas_sifir` masih diterima untuk kompatibilitas.
- Data Guru wajib `name`, `kode_guru`, `phone`, `email`, `status`, `password`.
- Data Admin/User wajib `name`, `email`, `phone`, `role`, `password`, `status`.
- Import besar dikirim frontend dalam batch agar request tidak terlalu berat.

Contoh error yang baik:

```text
Baris 12: Kota "Gresikk" tidak ditemukan di master wilayah.
Baris 20: Kelas "Sifir AwaI A" tidak ditemukan di master kelas.
```

Contoh warning yang baik:

```text
Baris 12: Jenis santri tidak ditemukan di master; field dikosongkan.
Baris 15: Sekolah asal tidak ditemukan di master; field dikosongkan.
Baris 18: Provinsi tidak ditemukan di master wilayah; field dikosongkan.
```

## 8. Offline Sync

Karena aplikasi punya kebutuhan offline, aturan data lokal:

- cache harus menyimpan ID relasi;
- label boleh ikut disimpan untuk tampilan offline;
- pending sync harus mengirim ID;
- pending absensi wajib membawa `attendance_key`;
- pesan gagal sync harus menyimpan detail backend jika tersedia;
- event refresh harus tetap dikirim saat sync selesai dengan conflict atau error;
- conflict detection sebaiknya memakai ID, unique key, atau composite key;
- jangan hanya mengandalkan nama text.

Contoh:

```text
tanggal + class_id + mapel_id + jadwal_id + siswa_id
```

lebih aman daripada:

```text
nama_kelas + nama_mapel + nama_siswa
```

Aturan absensi offline terbaru:

- Jika absensi sudah completed di server lalu perangkat offline, data dikunci dan tidak boleh diabsen ulang, diedit, atau dibatalkan sampai online lagi.
- Pending offline boleh diedit offline hanya oleh actor yang membuat pending tersebut.
- Jika data server sudah masuk lebih dulu, pending offline yang sync belakangan harus menjadi conflict dan tidak boleh menimpa data server.
- Admin tetap full access untuk edit data final saat online, tetapi pending offline admin tetap tidak boleh mengalahkan data server yang sudah ada.
- Guru hanya boleh input/edit absensi miliknya sendiri dan jadwal yang ditugaskan admin.
- Waktu completed harus menampilkan actor dan jam lengkap sampai detik jika datanya tersedia.

## 9. Role Access

Admin:

- boleh kelola master data;
- boleh melihat laporan penuh;
- boleh mengatur logo dan pengaturan aplikasi.

Guru:

- akses dibatasi dari `teacher_id` atau relasi assignment;
- akses mapel dibatasi dari `mapel_guru.user_id`;
- menu operasional guru harus mengikuti assignment admin;
- menu `Buku Induk` role guru sudah diganti menjadi `Data Diri Guru` read-only yang mengambil data dari profil user/guru;
- absensi guru dikunci sesuai hari jadwal dan baru boleh input setelah `jam_mulai`; admin tetap full access tanpa lock jadwal;
- tidak boleh mengubah master penting sembarangan;
- tidak boleh melihat data pembayaran sensitif kecuali memang diberi izin.

Orang tua:

- hanya melihat siswa yang terhubung ke guardian/orang tua;
- tidak boleh melihat siswa lain;
- tidak boleh mengubah data akademik.

Jangan pakai nama untuk permission.

Gunakan:

```text
user_id
role_id
teacher_id
guardian_id
student_id
```

Gunakan `ActorResolver` untuk mengambil user aktif dan role aktif secara konsisten di controller. Jangan membuat cara baca actor sendiri-sendiri kecuali ada alasan khusus yang jelas.

## 12. Jika Ada Bug

Urutan analisa:

1. Reproduksi bug dari UI.
2. Cek request API yang dikirim.
3. Cek controller/service yang menerima.
4. Cek model dan relasi.
5. Cek isi tabel.
6. Cek apakah query masih pakai text mentah.
7. Cek apakah data master ada.
8. Cek apakah offline cache ikut terpengaruh.
9. Baru lakukan perubahan kecil dan terukur.

Contoh bug pembayaran terbaru:

- Log server menampilkan `POST /api/pembayaran` status `500`.
- Laravel log menunjukkan PostgreSQL menolak insert karena constraint `pembayaran_jenis_check`.
- Penyebabnya tipe pembayaran baru, misalnya `Kitab`, dikirim ke kolom legacy `pembayaran.jenis` yang hanya menerima kategori lama.
- Fix yang benar adalah menjaga `payment_type_id` sebagai sumber resmi dan mengisi `pembayaran.jenis` dengan kategori legacy aman, bukan menghapus constraint atau menyimpan label liar.

Contoh bug rekap pembayaran wali:

- Tombol download PDF wali dapat gagal jika route `pembayaran/rekap-siswa` hanya tersedia di grup admin.
- Route rekap siswa harus bisa diakses `admin,wali`, tetapi controller tetap wajib membatasi wali hanya ke anaknya sendiri.
- Frontend perlu fallback file/share jika `Printing.layoutPdf` tidak tersedia atau gagal di perangkat.

Contoh bug edit Data Santri:

- Jangan mengubah nilai kosong dari backend menjadi tanda `-` di form edit.
- Tanda `-` yang dikirim ke `email_siswa` akan dianggap string dan gagal validasi email.
- Sanitizer frontend harus mengubah kosong/`-`/placeholder menjadi `null` untuk field opsional.

Contoh bug absensi duplicate dan `Unknown`:

- Jika guru/admin mengubah absensi `Izin` menjadi `Hadir`, sistem tidak boleh membuat row baru.
- Backend create harus menolak `attendance_key` yang sudah ada sebagai conflict; edit data final harus lewat `PUT /api/absensi/{id}`.
- Payload absensi wajib membawa `class_id`, `mapel_id`, dan `jadwal_id`.
- Dashboard tidak boleh fallback ke `Unknown`; data absensi yang scope-nya tidak lengkap harus ditahan dari tampilan.
- Jika data lama sudah terlanjur duplicate, jalankan `attendance:repair-duplicates --dry-run` sebelum `--apply`.
- Setelah duplicate aman, migration unique `attendance_key` harus dijalankan agar database ikut mengunci data.

Contoh bug Cloudflare tunnel:

- Error `failed to dial to edge with quic: timeout: no recent network activity` biasanya masalah QUIC/UDP dari jaringan, bukan Laravel.
- Untuk uji cepat di Windows, gunakan `cloudflared tunnel --protocol http2 --edge-ip-version 4 --url http://127.0.0.1:8000`.

## 15. Catatan Refactor Terakhir

Refactor terakhir yang sudah masuk pola maintenance:

- `ActorResolver` menjadi resolver bersama untuk active actor dan role admin/guru/orang tua.
- `ReferenceResolver` dibuat lebih ketat untuk master siswa, wilayah, dan referensi penting agar typo tidak menjadi master data baru.
- Master asal sekolah siswa memakai `school_origins`; form Data Santri mengirim `school_origin_id`.
- Update 9 Mei 2026: `school_origins` punya metadata opsional `city_id`, `npsn`, `jenjang`, `alamat`, dan `status_sekolah`; data sekolah nasional sebaiknya di-import/cache lokal dari sumber resmi seperti referensi NPSN, bukan query internet langsung dari picker.
- Endpoint `GET /api/school-origins` menerima `city_id`, `search`, dan `limit`; jika kota dipilih, picker sekolah asal mengikuti kota/kabupaten siswa.
- Master pekerjaan tetap satu tabel `occupations`; UI memfilter `Ibu Rumah Tangga` agar tidak tampil di pekerjaan ayah, tetapi tetap tampil di pekerjaan ibu/wali.
- Jenis santri input baru dibatasi ke `Santri Pondok`, `Santri Madin`, dan `Keduanya`.
- Jadwal memakai `teacher_id` dari user role guru, bukan label guru.
- Mata pelajaran memakai `guru_ids` dari user role guru dan assignment disimpan di `mapel_guru`.
- Absensi memvalidasi kecocokan `jadwal_id`, `class_id`, dan `mapel_id`.
- Absensi terbaru memakai `attendance_key` stabil dengan aturan server-first: `POST` create-only conflict-safe, `PUT` untuk edit final, dan sync offline tidak boleh overwrite data server.
- Dashboard mengabaikan absensi incomplete sehingga tidak menampilkan card `Unknown`.
- Command `attendance:repair-duplicates` tersedia untuk audit dan repair data lama.
- Seeder `RealtimeDummySeeder` menambah 10 siswa dan 10 wali terhubung untuk uji realtime.
- Jadwal aktif menolak bentrok guru yang sama pada hari/jam yang overlap.
- Update 9 Mei 2026: bentrok kelas tidak lagi ditolak jika guru/mapel berbeda, karena admin perlu mengatur banyak kelas/guru/mapel secara paralel.
- Sync absensi offline menyimpan pesan gagal yang lebih spesifik dan mengirim refresh event saat ada gagal/conflict.
- Nilai dan hafalan mewajibkan actor aktif; guru hanya boleh menilai mapel yang menjadi assignment-nya.
- Menu Nilai mengambil dropdown kelas dari master resmi `classes`.

- Update 9 Mei 2026: input absensi guru dikunci frontend dan backend sampai hari jadwal serta `jam_mulai`; guru masih boleh input sampai akhir hari jadwal.

## 17. Update 2 Juni 2026: Catatan Maintenance Stabilitas Sistem

Area yang wajib dijaga setelah update terbaru:

- Jangan menghapus `database/schema/pgsql-schema.sql`; file ini masih menjadi baseline struktur PostgreSQL.
- Jangan menganggap file controller/model/service baru sebagai sampah walaupun masih untracked di Git.
- Jika membersihkan project, yang aman dibersihkan hanya artefak generated seperti `build/`, `.dart_tool/`, dan `android/.gradle/`.
- Setelah cache Flutter dibersihkan, jalankan ulang `flutter pub get`.
- Pada Windows, build plugin Flutter membutuhkan symlink support. Jika muncul pesan symlink, jalankan terminal/IDE sebagai Administrator atau aktifkan Developer Mode.
- File nyasar seperti `absensi_backend/active())` boleh dihapus karena hanya output error PsySH, bukan source project.

Pola aman bottom sheet/modal:

- Setelah simpan berhasil, bottom sheet menutup dengan `Navigator.pop(context, result)`.
- Parent melakukan refresh setelah `await showModalBottomSheet` selesai.
