# PANDUAN BELAJAR PRESENTASI PROYEK

Update: 29 Mei 2026
Project: Absensi Android + Laravel Backend

Dokumen ini untuk belajar menjelaskan proyek secara runtut. Ini bukan pengganti `PANDUAN_BELAJAR_INTI.txt`. File inti tidak diubah.

## 1. Gambaran Umum Aplikasi

Aplikasi ini adalah sistem manajemen madrasah/sekolah berbasis Android dengan backend Laravel.

Fitur utama:

- login multi role;
- dashboard admin;
- dashboard guru;
- data diri guru read-only untuk role guru;
- dashboard orang tua/wali;
- biodata siswa untuk wali sebagai monitoring read-only dan PDF;
- buku induk siswa;
- data pondok atau setting pondok untuk komplek, kamar, dan santri pondok;
- data guru;
- kelas dan mata pelajaran;
- jadwal;
- absensi;
- nilai dan hafalan;
- pembayaran;
- export PDF/Excel;
- upload foto profil;
- upload logo dokumen;
- pengaturan tanda tangan dokumen;
- pengaturan keamanan pembayaran admin;
- import Excel data siswa, guru, dan admin/user;
- import siswa otomatis menghubungkan siswa ke kelompok belajar melalui kolom `kelompok_belajar`;
- import siswa memberi warning untuk data master opsional yang typo, tanpa menyimpan label liar;
- Data Santri memakai pilihan master resmi dan pilihan wali `Ayah`, `Ibu`, atau `Wali`;
- tempat lahir santri/ayah/ibu dipilih dari master Kota/Kabupaten agar tidak typo;
- data wali otomatis mengikuti data ayah/ibu jika wali sama dengan ayah/ibu, termasuk pekerjaan wali;
- asal sekolah siswa memakai master `school_origins`, bukan text bebas;
- Data Santri punya dua sekolah asal: sekolah asal sebelumnya dan sekolah asal siswa sekarang/terdaftar;
- Edit Data Santri memakai picker sekolah yang stabil dan bisa mencari master sekolah tanpa wajib memilih kota terlebih dahulu;
- master sekolah bisa ditambah/diedit admin dari aplikasi dan tetap masuk ke master `school_origins`;
- Data Santri memiliki alamat lengkap ayah, alamat lengkap ibu, status mondok, tanggal diterima pondok, dan tanggal diterima sekolah/akademik;
- admin bisa mengatur tahun ajaran dan semester aktif dari Buku Induk > Setting Akademik;
- admin bisa mengatur komplek, kamar, dan santri pondok dari Buku Induk > Data Pondok;
- admin bisa menekan `Sinkronisasi Data Santri` agar santri aktif masuk ke tahun ajaran/semester tertentu sebagai histori;
- tahun ajaran baru awalnya kosong sampai data santri disinkronkan, sehingga pembayaran/tagihan lama dan baru lebih akuntabel;
- input akademik dan pembayaran baru mengikuti tahun ajaran/semester aktif, sedangkan data lama tetap menjadi riwayat;
- admin bisa mengatur hak akses menu role guru dan wali dari aplikasi;
- backend juga menolak API jika permission dimatikan, jadi bukan hanya menyembunyikan menu di frontend;
- audit log mencatat perubahan penting untuk jejak keamanan ISO-aligned;
- master sekolah bisa dicari dan difilter berdasarkan provinsi, kabupaten/kota, dan kecamatan, serta disiapkan untuk import/API resmi;
- jenis santri input baru hanya `Santri Pondok`, `Santri Madin`, dan `Keduanya`;
- upload foto santri dan dokumen akta tersimpan sebagai berkas server;
- wajib ganti password pertama untuk guru dan wali;
- reset password user oleh admin;
- feedback sukses dan pull refresh yang lebih hidup tetapi tetap konsisten;
- realtime in-app untuk refresh data saat aplikasi aktif;
- tombol PDF pembayaran wali muncul hanya saat transaksi pembayaran sudah ada;
- pembayaran memiliki sistem tagihan aktual untuk sekali bayar dan bulanan;
- tagihan bulanan otomatis dibuat per periode, tidak dobel, dan bisa muncul ke admin serta wali;
- pembayaran SPP/bulanan bisa diproses per bulan akademik Jul-Jun dan bulan yang sudah lunas tidak bisa dibayar ulang;
- pembayaran SPP/bulanan sekarang mengikuti semester aktif: Ganjil menampilkan Jul-Des dan Genap menampilkan Jan-Jun;
- cek tagihan per santri membaca data tagihan yang ada tanpa membuat tagihan baru diam-diam;
- admin bisa membuka Pembayaran > Per Santri untuk mencari santri dan melihat tagihan lengkap per tahun ajaran/semester;
- Wali Santri melihat ringkasan tagihan anak, pembayaran bulanan, pembayaran umum, dan riwayat dengan tampilan yang sama rapi;
- pembayaran dan tagihan menampilkan label periode seperti `2025/2026 • Genap`;
- pembayaran bulanan ditampilkan dengan urutan tahun ajaran `Jul` sampai `Jun`;
- notifikasi tagihan disiapkan untuk in-app sekarang dan WhatsApp/email pada tahap lanjutan;
- menu Nilai mengambil kelas dari master resmi dan menampilkan siswa/mapel sesuai kelas;
- admin full access melihat semua mapel aktif untuk nilai/materi/absensi, sedangkan guru hanya sesuai jadwal dan mapel dari admin;
- pada menu Absensi admin, mapel aktif tanpa jadwal kelas tetap terlihat tetapi belum bisa dipakai simpan absensi sampai jadwal valid dibuat;
- absensi diperkuat agar edit atau input ulang data yang sama menjadi update, bukan duplicate;
- dashboard tidak lagi menampilkan absensi tidak valid sebagai `Unknown`;
- jadwal aktif menolak bentrok guru yang sama dan membolehkan jadwal paralel guru/mapel berbeda;
- jadwal multi-kelas dalam satu grup bisa disimpan tanpa bentrok palsu selama memang satu sesi yang sama;
- jadwal mapel dengan guru, kelas, dan mapel yang sama tetapi hari/jam berbeda tetap tampil semua;
- hapus guru pengajar dari mata pelajaran membersihkan jadwal guru tersebut dengan aman;
- jadwal yang punya histori absensi tidak dihapus permanen, tetapi dinonaktifkan agar arsip absensi tetap aman;
- status absensi guru di dashboard dan menu Absensi sudah sinkron sehingga `Upcoming` tidak membuka form;
- guru boleh absen mulai jam mulai sampai akhir hari jadwal, sedangkan admin tetap full access;
- Izin Guru dinonaktifkan sementara dan dibersihkan dari app layer karena bug, tetapi database lamanya tetap disimpan untuk rebuild nanti;
- tambah Guru Pengajar di Edit Mata Pelajaran sekarang langsung tersimpan ke backend sebelum jadwal dibuat;
- picker Tempat Lahir kota/kabupaten diperbaiki agar saat dibuka ulang tetap menampilkan daftar lengkap, bukan hanya pilihan terakhir;
- picker Tempat Lahir siswa/ayah/ibu dibuat lebih aman agar tidak muncul layar merah saat memilih Kota/Kabupaten;
- nilai lama seperti `Gresik` otomatis diarahkan ke nama master resmi seperti `Kabupaten Gresik` jika cocok;
- menu Absensi guru/admin menampilkan jumlah santri dan mapel aktif per kelas berdasarkan data realtime `class_id`;
- admin bisa mengelola master asal sekolah dan Data Santri menyimpan `school_origin_id`;
- admin bisa membuat tipe pembayaran bulanan dengan tanggal jatuh tempo dan generator tagihan otomatis;
- form pembayaran admin bisa memilih tahun ajaran dan semester, default mengikuti Setting Akademik aktif;
- hafalan ikut memiliki tahun ajaran dan semester agar rekap nilai/hafalan lebih konsisten;
- tersedia 10 siswa dan 10 wali dummy terhubung untuk uji realtime;
- responsif prioritas diperkuat untuk login, dashboard, pembayaran wali, nilai, buku induk, absensi, mapel, menu grid, dan bottom navigation;
- mode offline dan sinkronisasi.

## 3. Kenapa Database Dirombak

Sebelumnya banyak data berpotensi disimpan sebagai text bebas.

Masalah dari text bebas:

- typo bisa masuk;
- nama yang sama bisa punya banyak versi;
- query sulit dilacak;
- laporan bisa tidak konsisten;
- import Excel rawan salah;
- offline sync bisa bentrok;
- permission role bisa berbahaya jika berdasarkan nama.

Contoh masalah:

```text
Diki
DIKI
Diky
Diki Ramdhani
```

Sistem baru diarahkan agar relasi memakai ID.

## 4. Konsep ID sebagai Sumber Kebenaran

Yang ditampilkan ke user:

```text
Nama guru: Ust. Diki
Kelas: Sifir Awal A
Mapel: Akhlaq
Kota: Gresik
```

Yang disimpan sebagai relasi utama:

```text
teacher_id
class_id
mapel_id
city_id
```

Dengan begitu, kalau ada kesalahan input, data bisa dilacak dari ID.

## 5. Master Data

Master data adalah tabel referensi.

Contoh:

```text
roles
student_statuses
attendance_statuses
payment_methods
payment_statuses
classes
school_origins
mapel
provinces
cities
districts
villages
```

Manfaat:

- pilihan input lebih terkontrol;
- data tidak dobel;
- typo bisa dicegah;
- laporan lebih konsisten;
- sistem web dan Android bisa memakai data yang sama.

## 6. Wilayah Indonesia

Wilayah sudah dibuat sebagai master data:

```text
provinces
cities
districts
villages
```

Setiap wilayah punya:

```text
id
external_code
name
parent_id
```

Saat presentasi, jelaskan:

- user memilih nama wilayah di UI;
- backend menyimpan ID wilayah;
- kode resmi wilayah tetap ada di `external_code`;
- typo seperti `Gresikk` tidak boleh diterima sebagai kota baru.

## 7. Role Aplikasi

Admin:

- mengelola data master;
- mengelola siswa, guru, pembayaran, laporan, logo dokumen;
- mengatur hak akses menu guru/wali;
- mengatur tahun ajaran dan semester aktif;
- punya akses penuh dan tidak boleh terkunci dari menu inti.

Guru:

- mengisi absensi;
- mengelola data sesuai jadwal dan mata pelajaran yang dipilihkan admin;
- tidak boleh melihat data sensitif yang bukan haknya.

Orang tua/wali:

- melihat data anak yang terhubung;
- melihat nilai, absensi, pembayaran sesuai izin sistem.
- melihat biodata anak terbaru dan cetak/download PDF biodata;
- tidak boleh mengedit data akademik, siswa, pembayaran, jadwal, atau mapel.

Catatan penting role:

- Aplikasi hanya punya 3 role login: Admin, Guru, dan Wali Santri.
- Santri/Siswa bukan akun login; santri/siswa adalah data anak yang dikelola dan dihubungkan ke wali.
- Hak akses menu guru dan wali bisa diatur admin, tetapi admin tetap full access.

Admin:

- full access untuk semua data aktif;
- mengatur mapel, jadwal, guru, siswa, nilai, absensi, pembayaran, dan master data;
- mapel nonaktif tidak muncul di menu operasional sampai diaktifkan kembali.

Permission harus berbasis ID:

```text
role_id
user_id
teacher_id
guardian_id
student_id
```

Pada refactor terbaru, pembacaan user aktif dipusatkan lewat `ActorResolver`. Tujuannya agar controller tidak membaca actor dengan cara berbeda-beda.

## 10. Offline First

Konsep offline:

- aplikasi bisa menyimpan data sementara;
- saat online, data dikirim ke backend;
- data offline harus membawa ID relasi;
- label text boleh disimpan untuk tampilan offline.

Contoh yang baik:

```text
student_id = 5
class_id = 2
attendance_status_id = 1
label = Hadir
```

## 11. Penguatan Sistem Terbaru

Bagian ini bisa dijelaskan sebagai peningkatan kualitas sistem, bukan perubahan tampilan.

Yang diperkuat:

- master data siswa dan wilayah tidak otomatis dibuat dari typo;
- import siswa lebih aman: field wajib tetap error, field master opsional typo dikosongkan dengan `warnings`;
- template Excel siswa menjelaskan status resmi, jenis santri resmi, dan aturan master data;
- master asal sekolah `school_origins` mencegah penulisan asal sekolah bebas seperti variasi huruf yang tidak resmi;
- jenis santri sekarang dibatasi ke `Santri Pondok`, `Santri Madin`, dan `Keduanya`;
- menu Nilai memakai master kelas `classes`, lalu siswa dan mapel mengikuti `class_id`/jadwal aktif;
- penilaian menampilkan pesan jelas jika belum ada mapel aktif untuk kelas yang dipilih;
- absensi memakai `attendance_key` stabil dari tanggal, kelas, mapel, jadwal, dan siswa;
- absensi create sekarang conflict-safe berbasis `attendance_key`; jika data untuk scope yang sama sudah masuk server, request baru ditolak sebagai conflict dan tidak membuat data double;

```text
Data Pondok dibuat sebagai master resmi untuk mengelola komplek, kamar,
dan santri pondok. Relasi santri ke kamar tidak memakai text bebas, tetapi
memakai ID master database agar tidak terjadi typo dan data dobel.
```

Hal penting:

- Komplek dan kamar adalah master data.
- Santri pondok hanya boleh punya satu relasi aktif.
- Santri yang sudah masuk pondok tidak muncul lagi di form tambah.
- Pindah kamar dilakukan melalui edit, bukan tambah ulang.
- Santri yang diaktifkan kembali otomatis ikut kegiatan sholat.

### 2. Absensi Jama'ah Sholat

Kalimat presentasi:

```text
Absensi Jama'ah Sholat mengikuti pola Absensi Madin, tetapi konteksnya
berdasarkan komplek dan kamar. Admin atau guru bisa menginput status M, I,
dan S, lalu data langsung masuk ke rekap, dashboard, wali, dan notifikasi.
```

Hal penting:

- `M` berarti Masuk.
- `I` berarti Izin.
- `S` berarti Sakit.
- Data membaca santri aktif dari Data Pondok.
- Dashboard menghitung total hari ini.
- Wali hanya melihat absensi anak sendiri.
- Guru hanya melihat komplek/kamar sesuai akses jika dibatasi admin.

### 3. Keuangan dan CMS Pembayaran

Kalimat presentasi:

```text
Keuangan sekarang memakai konsep master tagihan. Admin bisa mengatur tipe
pembayaran, metode pembayaran, dan periode pembayaran dari CMS, sehingga
aturan pembayaran tidak perlu di-hardcode di aplikasi.
```

Hal penting:

- Metode pembayaran bisa aktif/nonaktif.
- Periode pembayaran bisa bulanan, semesteran, tahunan, sekali bayar, atau umum.
- Pembayaran umum tidak otomatis lunas jika bayar kurang.
- Status tagihan dihitung dari tagihan, dibayar, dan kekurangan.
- Pembayaran bulanan menampilkan centang pada bulan yang sudah lunas.
- Admin dan wali membaca status tagihan dari sumber yang sama.

### 4. Role dan Hak Akses

Kalimat presentasi:

```text
Role admin dibuat lebih fleksibel. Admin utama punya full access, sedangkan
admin bendahara, admin pondok, admin absensi, atau admin akademik bisa dibatasi
sesuai hak akses menu.
```

Hal penting:

- Admin utama tidak boleh terkunci dari fitur inti.
- Bendahara fokus ke keuangan.
- Admin pondok fokus ke Data Pondok.
- Admin absensi fokus ke input dan rekap absensi.
- Wali hanya monitoring data anak.
